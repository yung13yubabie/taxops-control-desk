# 啟動與資料庫單例保護

單一 EXE 的每次啟動都可能先由打包程式解壓到不同的暫存目錄。資料庫與
啟動鎖不能放在該目錄，也不能以目前工作目錄作為共同鎖的位置。

## 順序與邊界

1. 建立 Qt 應用、載入中文與圖示。
2. 以 `QLockFile` 取得同一使用者、同一應用名稱的原子鎖。
   檔案位於本機應用資料目錄的 `.instance-locks`，名稱由完整應用名稱雜湊產生。
3. 取得鎖後才建立本機通知端點、開啟／升級資料庫及顯示主視窗。
4. 關閉資料庫後釋放通知端點及所持有的檔案鎖。釋放動作可重複呼叫。

`QLocalServer` 用來通知原視窗，並不作 Windows 的原子互斥保證。
取得鎖失敗時，程式嘗試傳送通知。若通知端點尚未出現，僅在尚未寫入任何資料前，
以共用期限和短暫間隔重試指定的連線錯誤；一旦開始寫入，失敗也不重送。
通知失敗可再取得鎖一次，以涵蓋原程序剛好退出。
仍無法取得時，清楚告知稍候重試並停止，不開啟資料庫。寫入鎖目錄或磁碟失敗
會顯示可操作的繁體中文訊息，不假裝已有視窗成功切換到前景。

## 過期檔案與恢復

- `setStaleLockTime(0)`：不會只因執行時間長，就刪除仍在使用中的鎖。
- 過期判定交給 Qt 的 PID／程序名稱與系統檔案控制，不自行刪除鎖，也不終止其他程序。
- 同 PID、同程序名稱被重用或主機資訊無法確認时，保守拒絕開啟。
- Qt 官方記載 Windows 非 ASCII 主機名稱可能影響過期偵測。因此不能保證每種
  強制中止都自動恢復；先等舊程式退出，仍受阻時重新啟動電腦後再試。
- 舊版程式不遵循新增檔案鎖；使用新版候選前必須先關閉舊版。通知端點的
  相容性探測不能取代這項限制。

[Qt QLockFile 說明](https://doc.qt.io/qt-6.10/qlockfile.html)
說明了共同路徑、長期鎖、PID 重用與 Windows 主機名稱限制。
[Qt QLocalServer 說明](https://doc.qt.io/qt-6.10/qlocalserver.html#listen)
記載 Windows 可有多個服務監聽相同名稱。

## 驗證要求

`test_atomic_instance_lock.py` 在合成目錄驗真實檔案鎖、失敗關閉、活躍／重用 PID
資料保留、子程序中止後重試及資料庫關閉順序。該檔明確隔離通知端點，不能當作
完整 IPC 通過。`test_single_instance.py` 保留真實跨程序通知整合。

Windows 單一 EXE 門檻另需同步啟動兩個實際 EXE，證明只有一個進入資料庫／視窗；
再驗正常關閉、獨立合成程序中止、重新啟動與暫存解壓清理。Linux 合成測試不能
代替這些 Windows 證據，也不能代替乾淨最低版本 Windows 的手動驗收。

通知的應用層共用預算與 Windows 原生呼叫的限制，見
[通知與啟動時序契約](instance_activation.md)。未宣稱能中斷 Qt 內部的原生等待；
也不把傳送端排空佇列當作接收端視窗已可用的證明。
