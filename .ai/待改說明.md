## 必修 Blocker 1：滯納金服務層可保存非法期別

Evidence：
- `src/taxops/services/late_fee.py:137` 的 `calculate_and_save()` 未驗證 `payload.period_code`。
- `src/taxops/services/late_fee.py:182-185` 直接把 `period_year` / `period_code` 寫入 DB。
- Codex probe 實測：直接呼叫 service，`period_code="13-14"` 會成功保存為 late_fee_records，而不是 raise `late_fee.period.invalid`。

Root Cause：
- UI 期別下拉有 allowlist，但核心 service 沒有重做 allowlist validation。
- 既有測試只測 `last_payment_date_for_period("13-14")` 會 raise，沒有測 `calculate_and_save()` 的 direct-service path。

Minimal Patch：
- 在 `LateFeeService.calculate_and_save()` 開頭加核心層驗證：
  - 若 `payload.period_code is not None` 且不在 `PERIOD_CODES`，raise `LateFeeValidationError("late_fee.period.invalid")`。
  - 若 `payload.period_year is not None` 但 `period_code is None`，也應拒絕或清楚定義；建議拒絕，避免保存半套期別資料。
  - 若 `period_code is not None` 但 `period_year is None`，也拒絕。
- 新增 regression test：
  - `test_calculate_and_save_rejects_invalid_period_code`
  - `test_calculate_and_save_rejects_partial_period_fields`
  - assert DB 沒有新增 late_fee_records。

Verification：
- 先跑新增測試，確認修補前會紅、修補後會綠。
- 再跑：
  - `python -m pytest tests/test_late_fee.py tests/test_late_fee_page.py tests/test_db_migrations.py -q --tb=short`

## 問題清單

### P0-1：Dashboard 篩選狀態污染側邊欄導航

現象：

- 使用者從 Dashboard 卡片切入待辦、案件、覆核等頁面後，頁面 `_filter_key` 被設成 Dashboard 篩選。
- 之後從側邊欄直接進該頁，仍沿用舊 `_filter_key`。
- 新增的案件、待辦、意見若不符合舊篩選，刷新後就從畫面消失，看起來像資料沒保存。

證據位置：

- `src/taxops/ui/main_window.py`
  - `navigate_to(page_id, filter_key="")` 只在 `filter_key` 有值時呼叫 `page.set_filter(filter_key)`。
  - `_on_nav_changed()` 只呼叫 `_activate_page(idx)`，沒有清除 filter。
- `src/taxops/ui/pages/tasks_page.py`
  - `set_filter()` 設定 `self._filter_key`。
  - `refresh_context()` 只 reload，不清空 `_filter_key`。
- `src/taxops/ui/pages/engagements_page.py`
  - 同樣保留 `_filter_key`。
- `src/taxops/ui/pages/review_notes_page.py`
  - 同樣保留 `_filter_key`。
- `src/taxops/ui/pages/clients_page.py`
  - 也有 `_filter_key`，需一併檢查 lease expiring filter 是否殘留。

最小修正：

1. 建立明確頁面協議：有 Dashboard filter 的頁面都加 `clear_filter()`。
2. `MainWindow._on_nav_changed()` 代表使用者從側邊欄直接進入，應呼叫目前頁面的 `clear_filter()` 再 `refresh_context()`。
3. `MainWindow.navigate_to(page_id, filter_key=...)` 代表 Dashboard 或程式導向：
   - 有 `filter_key`：先進頁，再套 `set_filter(filter_key)`。
   - 無 `filter_key`：不要保留前一次 Dashboard filter。
4. 加測試：Dashboard 切待辦 overdue 後，再用側邊欄進待辦，必須顯示全部待辦。

驗收：

- 從 Dashboard 點「逾期待辦」只看到逾期。
- 再點側邊欄「待辦事項」必須回到全部待辦。
- 新增一筆非逾期待辦後不會消失。
- 同樣覆蓋案件管理、覆核意見、客戶租約到期篩選。

### Step 1：修 Dashboard filter 污染與各頁查看全部

Root cause：

- `MainWindow._on_nav_changed()` 從側邊欄進頁沒有清除頁面的 Dashboard filter。
- `TasksPage`、`EngagementsPage`、`ReviewNotesPage`、`ClientsPage` 的 `_filter_key` 會殘留。
- `EngagementsPage` 沒有「全部客戶」視圖。
- `AttachmentsPage` 有全部案件選項但不載入全部附件。
- `DocumentRequestsPage` 側邊欄直接進入沒有全域索件清單。

要求：

- 建立 `clear_filter()` 協議。
- 側邊欄進入主頁時清除 Dashboard filter。
- Dashboard 卡片導航仍可套指定 filter。
- 各主頁都能從本頁查看全部資料。
- 新增 regression tests。

驗收：

- Dashboard 進待辦 overdue 後，再側邊欄進待辦，必須顯示全部。
- 新增一筆非 overdue 待辦後不會消失。
- 案件、覆核、客戶租約到期 filter 同樣不污染。
- 附件頁「全部案件」顯示所有附件。
- 索件管理側邊欄進入可看到所有索件批次。

### Step 2：索件文件項目批量新增、編輯、刪除

要求：

- 多行批量新增文件項目。
- 編輯文件項目名稱/備註。
- 刪除文件項目，需二次確認與 audit。
- request status 需重新計算。
- 禁止假成功：部分成功必須明確回報。

驗收：

- 貼上 5 行新增 5 筆。
- 空白行忽略，全空拒絕。
- 編輯後 DB 更新、audit 有紀錄。
- 刪除後清單消失、audit 有紀錄。
- 錯誤資料不寫 DB。

### Step 3：固定開立新增方案入口

要求：

- 固定開立頁必須有永遠可見的「新增方案」按鈕。
- 沒有任何方案時也能建立第一筆。
- 全部客戶模式下新增方案要先選客戶。

驗收：

- 空資料固定開立頁可新增第一個方案。
- 儲存後出現在畫面。
- 原本 accordion 內新增方案仍可用。

### Step 4：附件刪除可見化與 EXE

要求：

- 保留軟刪除：status=`archived`，audit=`attachment.delete`，檔案保留。
- UI 按鈕在小視窗不可消失；必要時放入「更多」。

- 選附件後刪除按鈕啟用。
- 刪除後清單消失、DB archived、audit 存在。

- 先補或更新測試。
